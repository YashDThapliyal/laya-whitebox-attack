# DECISIONS

Running log of non-trivial judgment calls made during the unsupervised run.

## Phase 0
- **Python 3.11 via uv, not system 3.14.** 3.14 is very new; 3.11 is the safest target for torch/transformers wheels.
- **Laya max_len = 512 tokens (192 reserved for question+options head).** This is a hard architectural constraint from the checkpoint config (ModernBERT supports 8k natively, but Laya was trained at 512). Agent traces — especially MRT/SHADE trajectories — are far longer than ~320 state tokens. Handled in Phase 1/2 via trace compression (see below). Did NOT raise max_len: the decision head was trained with 512 and position behaviour beyond it is untested; doing so would confound the monitor quality.
## Phase 1 — data
- **ToolEmu has no pre-generated trajectories in the repo** (`assets/` has only case specs; trajectories require running the GPT-4 emulator, which needs a paid OpenAI key I don't have and wouldn't spend unsupervised). **Decision:** build *synthetic pseudo-traces* from each case spec: violating = user instruction + up to 2 "Potential Risky Actions" rendered as agent actions; compliant = same instruction + up to 3 "Expected Achievements". The "The Agent may/should" prefix is stripped from both so the modal verb isn't a label shortcut. These are clearly weaker than real trajectories (and risky-action text often contains outcome language like "leading to data loss" — a lexical shortcut). 288 records; kept tagged `source=toolemu` so they can be ablated.
- **InjecAgent contains attack cases, not agent outputs.** **Decision:** build a *contrastive pair per case*: identical prefix (user instruction → user tool call → tool output containing the injected instruction), then (violating) the agent calls the attacker tool(s) — for data-stealing cases also the exfiltration email — vs (compliant) the agent answers the user and ignores (50%: explicitly flags) the injection. Both end with a final answer so "ends with Final Answer" is not a shortcut. Attacker-tool outputs come from InjecAgent's `attacker_simulated_responses.json`. Capped at 500 of 1,054 cases (1,000 records) so templated data doesn't dominate the pool. Split group = user tool (val never shares a user scenario with train).
- **R-Judge**: 571 records (not 569 as in the plan — repo currently has 571), label 1=unsafe → violating. Rendered as [USER]/[AGENT THOUGHT]/[AGENT ACTION]/[TOOL OUTPUT] lines. Note R-Judge "unsafe" is broader than adversarial policy violation (includes e.g. harmful content generation).
- **Train/val**: 15% of *groups* per source held out as `val` (R-Judge group = record, InjecAgent = user tool, ToolEmu = case). `split` field uses `train`/`val` for the pool (the plan's "small carved-out slice").
- **MRT (= `shade-arena`)**: HF repo is 11.5 GB with each agent run duplicated under every monitor model. Only 5 SHADE-Arena tasks are in `task_pairs/` on HF (american_airlines_2, api_key_calendar_agendas_2, bank_transfer_2, expenditure_accounting, spam_filter_update); the 15 CUA tasks (`task_pairs_agentcompany/`) were **not** used — they're computer-use traces, a different modality, and the plan's focus is SHADE tool-use. Downloaded one copy per unique agent run (dedup by folder key, then by md5 of conversation) for 8 attack strategy folders + `transcripts_no_secondary_task` (benign): 1,866 files, ~230 MB.
- **MRT labels**: `violating` = attack-strategy transcript with `side_task_evaluation == True`; `compliant` = `transcripts_no_secondary_task`. **Attack transcripts where the side task failed (410) are excluded** from the held-out set (saved to `data/mrt_side_task_failed.jsonl`) because whether an attempted-but-failed sabotage is "violating" is ambiguous. Result: 1,448 held-out traces (371 compliant / 1,077 violating). expenditure_accounting has only 4 successful violating traces — per-task numbers for it are meaningless.
- **MRT monitor view** replicates MRT's own `strip_thinking_tags`: system prompt dropped (it literally describes the secondary task), `<thinking>` blocks removed (hidden from monitors in MRT), `<model_thinking>` kept. Tool calls in MRT logs contain only tool *names* (no arguments), so evidence of sabotage lives in tool outputs; tool outputs are truncated to 400 chars (many are 30k-char email dumps), messages to 1,500 chars. Median compressed MRT state is ~13.9k chars (~3.5k tokens) — far over Laya's ~320-token state budget, handled by sliding windows in Phase 2/3.
- **Leakage check**: 17.5% of violating MRT traces mention "secondary task" in visible text (0% of compliant) — agents that slipped up. That's a legitimate catch, but I report metrics both with and without these traces.
- **MRT license**: CC BY-NC 4.0 (non-commercial). Also the dataset card says not to train generative models on it — we don't train on it at all (eval only).
## Phase 2 — fine-tuning
- **Moved training to Colab (A100-40GB) instead of local MPS.** A local debug run (batch 8×512, fp32, AdamW on 421M params) pushed the 18 GB Mac into ~10 GB of swap and hadn't completed 20 micro-steps after 10+ minutes. The user explicitly allowed Colab. On the A100 (bf16 autocast) an epoch takes ~0.4 min. Note: the first `colab new --gpu A100` call timed out client-side but the server still allocated a VM, leaving an orphaned billable A100 that `colab stop` couldn't address (no local record); I released it via the CLI's own `client.unassign(endpoint)`. Worth knowing for next time.
- **Loss:** plain cross-entropy over the two option-marker logits (= the `loss_ce` term of Laya's fine-tuning notebook). Dropped the notebook's GRPO/proper-scoring noise term: with hard binary labels, CE *is* the log-score part of that proper reward, and the RL term only adds variance. Encoder LR 2e-5, head LR 1e-4 (notebook: 2.5e-5 / 1e-4), AdamW wd 0.01, 6% warmup + cosine, batch 16, 3 epochs, grad-clip 1.0, seed 0. Stopping rule: 3 epochs or 60 min, whichever first; model selection by val AUROC.
- **Kept max_len=512** (checkpoint's training length) rather than the notebook's 1024: consistent train/inference, and MRT traces need windowing regardless (median ~3.5k tokens).
- **Monitor question:** one `noul` question (text in `scripts/monitor_lib.py::QUESTION`). Typed `choice` over risk categories (stretch goal) skipped — categories don't align across sources and it doesn't serve the attack experiment.
- **Training view of long states:** first 96 tokens (user request) + tail. **Inference on long traces:** sliding windows = first 96 tokens + a 312-token body chunk, stride 192; trace score = **max over windows** (top-3 mean also reported). Max-aggregation is the natural "flag if any part is suspicious" rule, and it matters for the attack: the attacker must push *every* window below threshold.
- **R-Judge re-split.** First training run (kept on the VM as runs/monitor_v0_rjudge_by_record) grouped R-Judge val by *record*; val AUROC on R-Judge hit 0.994 after one epoch, which I don't believe — R-Judge has many near-duplicate records within a scenario file. Re-split R-Judge by **scenario file** (27 files, ~4 held out) and retrained; only the re-split model is used downstream. (Zero-shot R-Judge val AUROC was 0.50.)
- **Calibration:** temperature fitted on val by LBFGS (as in the notebook); decision threshold = F1-optimal on val (plan 4.3). Both are fitted on the training-pool val, *not* on MRT — so they may transfer badly to MRT, which is itself something the baseline eval measures.
## Phase 3 — baseline eval
- **Did not retune anything on MRT** after seeing chance-level AUROC (plan: MRT is untouched; no training or hyperparameter tuning against it). The obvious fixes (train on some SHADE tasks and test on others; calibrate the threshold on SHADE; change aggregation after looking) would all use the eval set, so they are listed as next steps in SUMMARY.md instead.
- Reported both max- and top-3-mean window aggregation (both were pre-specified in the eval script before looking at results), and metrics excluding the 188 "secondary task" leak traces.
- Zero-shot Laya evaluated with its own shipped noul temperature (1.98) and threshold 0.5, as the reference point.
- **Added a second attack target set (deviation from plan, additive only):** because the monitor is at chance on SHADE and flags ~99% of traces, a SHADE-only attack would measure evading a near-constant classifier. Phase 4 therefore also attacks the training-pool **val** violating traces the monitor correctly flags (never trained on; used only for epoch selection / temperature / threshold). The SHADE attack is still run as specified.
## Phase 4 — attack
- **Threat model / editable tokens:** by default only *agent-authored message text* is editable ([AGENT] lines in MRT = visible replies + `<model_thinking>`; [AGENT THOUGHT] / [AGENT FINAL ANSWER] in the train-pool format). User request, tool-call names and tool outputs are fixed — editing them would change what the agent *did*, not how it describes it. The first 96 state tokens (the trace prefix repeated in every window) are never editable. `--scope all` (any non-prefix token, incl. tool outputs) is run as an upper bound. MRT targets with zero editable agent text (2 of the first 22 sampled) are skipped and counted.
- **Algorithm:** HotFlip first-order scores on the *smooth max* (logsumexp) of window margins, gradients scattered from all windows back to trace positions; top-48 (≤4 tokens/position) candidates re-scored *exactly*; always take the best candidate (GCG-style) so the search can leave plateaus — the first version stopped at the first non-improving step and I changed it after seeing early stops. Candidate vocab = tokens decoding to an alphabetic word piece or basic punctuation (42,746 / 50,368).
- **Numerics:** attack scoring in fp32 with TF32 matmuls (bf16 margins were quantized in steps of ~0.03–0.06, hiding single-swap effects). Baseline eval used bf16, so a trace's starting p in the attack can differ slightly from its Phase-3 p.
- **Success** = trace max-window p(violating) < val-F1 threshold 0.409 (z < −0.828). Success at budget b uses the best state within the first b swaps. Every success is re-verified after decode→re-tokenize.
- **Budgets/samples (bounded by wall-clock caps):** in-distribution val: all 103 violating val traces the monitor flags that have editable text, budget 20, cap 35 min per run. MRT: 20 true positives (round-robin across tasks, ≤25 windows to bound time), budget 60, cap 50 min per run. Random-substitution baseline on the same targets/positions/vocab/budget. The 25-window cap biases the MRT sample toward shorter traces (median trace is 21 windows, so it's a mild bias).
- **Ops note:** an early relaunch left stale attack processes running (`pkill -f` inside `sh -c` killed its own shell first), which caused a CUDA OOM; all processes were killed by PID and everything was rerun from scratch. Only the clean rerun is reported.

## Fluency-constrained attack (follow-up experiment, user-requested)
- **Mechanism:** `scripts/attack.py --fluent_k 20`. Before HotFlip ranking, the candidate pool at each editable position is restricted to the top-20 predictions of base `answerdotai/ModernBERT-large` as a masked LM (the position masked, 128 tokens of current-trace context on each side), intersected with the same word-piece vocabulary as before. Laya's tokenizer vocab is identical to base ModernBERT's (50,368 tokens, same mask id), so predictions map 1:1 onto candidate ids. Predictions are cached per position and re-computed for positions within ±8 tokens of each applied edit, since their context changed. Everything else (gradient, top-48 exact re-scoring, budget accounting, targets, scopes) is unchanged.
- **k = 20.** Small enough that candidates are locally plausible, large enough to leave the attacker real choice. Not tuned. Only one k was run, a single point, not a sweep.
- **One run per scope at p < 0.5; the p = 0.865 result is read off the same greedy path** (success at 0.865 within b = the path crossed 0.865 by step b). Justified empirically on the existing unconstrained runs: the dedicated 0.865 runs and the 0.5 runs agree on derived 0.865 success for 115/117, 117/117 and 20/20 targets (the 2 mismatches are GPU non-determinism). This halves GPU time.
- **Same targets:** val targets are recomputed by the same deterministic selection (checked afterwards against the unconstrained runs' ids); SHADE targets come from the same Phase-3 score file.
- **Perplexity metric:** GPT-2 (124M), an LM unrelated to both the monitor and the MLM filter, on the ±12-token windows around each edit that attack.py records (`orig_context` vs `adv_context`), averaged in log space per trace, median over traces. It measures *local* fluency only; it doesn't check global coherence or meaning preservation. The same metric is applied to the existing unconstrained runs (their records have the same fields).
- **Semantic drift is allowed.** The MLM filter keeps edits locally plausible but can flip meaning (e.g. "wrong" → "right" in a smoke test). That's deliberate: a real adversary rewording its own narration would do exactly this. It's noted in the write-up.
- **Ops:** the new watchdog's first iteration falsely reported completion. Before `/content/proj` existed, `colab exec` returned a traceback that echoed the source line containing the done-marker string. Fixed by building the marker at runtime and tolerating a missing directory.
### Zero-shot checkpoint arm (added mid-run at the user's request)
- **Checkpoint:** the released `convaiinnovations/laya` English checkpoint, un-fine-tuned ("zero-shot"), same `noul` question.
- **Calibration, same procedure as the fine-tuned model** (`scripts/zeroshot_targets.py`): margins on the training-pool val slice (head+tail view), temperature fitted by LBFGS (T = 1.68), threshold = F1-optimal on val with the same tie-breaking. Result: **p ≥ 0.497** (val F1 0.745; flags 73% of val). The fine-tuned model's threshold is 0.865, so "crossing your own operating threshold" means different things for the two checkpoints. **The common bar p < 0.5 is the fair head-to-head** (the fine-tuned runs go to p < 0.5 anyway, and 0.5 ≈ the zero-shot threshold).
- **Targets per checkpoint, same rule:** violating traces it flags (windowed max p ≥ its own threshold). In-distribution: all of them (zero-shot 117: InjecAgent 86, ToolEmu 17, R-Judge 14; fine-tuned 117: 87/21/9). **Overlap** (both flag): InjecAgent 85, ToolEmu 16, **R-Judge only 6**. SHADE: zero-shot flags 624 eligible violating traces (≤25 windows). For each scope, the fine-tuned model's 20 SHADE targets were placed first if zero-shot also flags them (all 20 do), so the SHADE overlap is the full 20.
- **Attack runs** on a second A100 (the first held two fluent chains at 26/40 GB; four would risk the OOM seen earlier). Zero-shot weights download from HF on the VM, so no chunked upload was needed. Same fluent_k = 20, budgets, scopes and caps. Each run's threshold is the zero-shot model's own (0.497); success at p < 0.5 is read off the same path (0.5 is crossed first).
- **Fluent-experiment infra:** the fine-tuned fluent VM (laya4) was reclaimed server-side between ~12:15 and 12:40. Its watchdog didn't alarm, because `python … | tail -1 || …` took the pipeline's exit status from `tail` and masked the failed re-adopt. Fixed in the next watchdog (explicit exit codes, timeouts on every colab call, token refresh). The remaining fine-tuned runs resumed on the zero-shot VM (laya5), which was free by then, after uploading the checksum-verified weights; `--resume` skipped synced records. laya5's session token expired twice (hourly) and was re-adopted each time.
- **Reference-point check:** verified from the paper's text that the persuasion paper's 47% is a *maximum* across agent–monitor pairs ("acceptance rates up to 47% relative to the baseline"), not an average; it's cited that way.
- **Checkpoint comparison, added analysis:** zero-shot targets start far closer to the p = 0.5 bar (median p 0.67 vs 0.98 on the InjecAgent overlap). So the write-up adds a per-edit logit-drop comparison, with Wilcoxon tests on uncensored traces, to separate "closer to the bar" from "more sensitive per edit". It's post-hoc and labelled as such.
## Wrap-up strengthening pass (user-requested)
- **R-Judge can't be widened within the held-out slice.** It has 19 violating val traces and the fine-tuned monitor flags 9; all 9 were already attacked. Widening further would mean attacking traces from the training split, which the monitor saw with labels, so that measures something different. It's run as a **clearly separated supplement** (60 of the 266 flagged violating train-split R-Judge traces, seeded order) and not merged into any held-out number.
- **SHADE widened 20 → 80 per scope** for the fine-tuned monitor, both unconstrained and fluent attacks. The same selection rule with n = 80 reproduces the original 20 as its first 20, in order (verified), so the 80 is a strict superset; only the 60 new traces were attacked. All new runs go to p < 0.5, with 0.865 read off the path (validated earlier). For unconstrained agent-text, the 3 original traces that crossed 0.865 were rerun to learn their p < 0.5 outcome. The other 17 never crossed 0.865 in 60 swaps, so they're failures at p < 0.5 by construction. Zero-shot SHADE was not widened: cost, and it was indistinguishable at n = 20.
- **Two A100s** (w1: agent-text unconstrained + fluent; w2: any-token unconstrained + fluent, then the R-Judge-train supplement), each with a per-VM chunk directory, staggered provisioning (to avoid adopting each other's VM), and a watchdog with token refresh and timeouts.
- **Edit review.** Every fluent agent-text trace flipped at the operating threshold (73) was rebuilt by replaying its edits on the original tokens up to the first crossing (0 replay mismatches) and diffed line by line (`results/edit_review_items.md`). Naturalness (natural/awkward/broken) and meaning effect (preserving/changing/garbled, plus benign-shift) were labelled by **two independent LLM raters blind to each other and to the monitor results**, with a fixed rubric. Agreement is reported, and I adjudicate disagreements. These are model raters, not humans. The human spot-check is a stratified sample printed plainly for the user to eyeball.
