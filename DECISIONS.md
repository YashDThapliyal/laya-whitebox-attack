# DECISIONS

Running log of non-trivial judgment calls made during the unsupervised run.

## Phase 0
- **Python 3.11 via uv, not system 3.14.** 3.14 is very new; 3.11 is the safest target for torch/transformers wheels.
- **Laya max_len = 512 tokens (192 reserved for question+options head).** This is a hard architectural constraint from the checkpoint config (ModernBERT supports 8k natively, but Laya was trained at 512). Agent traces — especially MRT/SHADE trajectories — are far longer than ~320 state tokens. Handled in Phase 1/2 via trace compression (see below). Did NOT raise max_len: the decision head was trained with 512 and position behaviour beyond it is untested; doing so would confound the monitor quality.
## Phase 1 — data
- **ToolEmu has no pre-generated trajectories in the repo** (`assets/` has only case specs; trajectories require running the GPT-4 emulator, which needs a paid OpenAI key I don't have and wouldn't spend unsupervised). **Decision:** build *synthetic pseudo-traces* from each case spec: violating = user instruction + up to 2 "Potential Risky Actions" rendered as agent actions; compliant = same instruction + up to 3 "Expected Achievements". The "The Agent may/should" prefix is stripped from both so the modal verb isn't a label shortcut. These are clearly weaker than real trajectories (and risky-action text often contains outcome language like "leading to data loss" — a lexical shortcut). 288 records; kept tagged `source=toolemu` so they can be ablated.
- **InjecAgent contains attack cases, not agent outputs.** **Decision:** build a *contrastive pair per case*: identical prefix (user instruction → user tool call → tool output containing the injected instruction), then (violating) the agent calls the attacker tool(s) — for data-stealing cases also the exfiltration email — vs (compliant) the agent answers the user and ignores (50%: explicitly flags) the injection. Both end with a final answer so "ends with Final Answer" is not a shortcut. Attacker-tool outputs come from InjecAgent's `attacker_simulated_responses.json`. Capped at 500 of 1,054 cases (1,000 records) so templated data doesn't dominate the pool. Split group = user tool (val never shares a user scenario with train).
- **R-Judge**: 571 records (not 569 as in the plan — repo currently has 571), label 1=unsafe → violating. Rendered as [USER]/[AGENT THOUGHT]/[AGENT ACTION]/[TOOL OUTPUT] lines. Note R-Judge "unsafe" is broader than adversarial policy violation (includes e.g. harmful content generation).
- **Train/val**: 15% of *groups* per source held out as `val` (R-Judge group = record, InjecAgent = user tool, ToolEmu = case). `split` field uses `train`/`val` for the pool (the plan's "small carved-out slice").
- **MRT (= `shade-arena`)**: HF repo is 11.5 GB with each agent run duplicated under every monitor model. Only 5 SHADE-Arena tasks are in `task_pairs/` on HF (american_airlines_2, api_key_calendar_agendas_2, bank_transfer_2, expenditure_accounting, spam_filter_update); the 15 CUA tasks (`task_pairs_agentcompany/`) were **not** used — they're computer-use traces, a different modality, and the plan's focus is SHADE tool-use. Downloaded one copy per unique agent run (dedup by folder key, then by md5 of conversation) for 8 attack strategy folders + `transcripts_no_secondary_task` (benign): 1,866 files, ~230 MB.
- **MRT labels**: `violating` = attack-strategy transcript with `side_task_evaluation == True`; `compliant` = `transcripts_no_secondary_task`. **Attack transcripts where the side task failed (410) are excluded** from the held-out set (saved to `data/mrt_side_task_failed.jsonl`) because whether an attempted-but-failed sabotage is "violating" is ambiguous. Result: 1,448 held-out traces (371 compliant / 1,077 violating). expenditure_accounting has only 4 successful violating traces — per-task numbers for it are meaningless.
- **MRT monitor view** replicates MRT's own `strip_thinking_tags`: system prompt dropped (it literally describes the secondary task), `<thinking>` blocks removed (hidden from monitors in MRT), `<model_thinking>` kept. Tool calls in MRT logs contain only tool *names* (no arguments), so evidence of sabotage lives in tool outputs; tool outputs are truncated to 400 chars (many are 30k-char email dumps), messages to 1,500 chars. Median compressed MRT state is ~13.9k chars (~3.5k tokens) — far over Laya's ~320-token state budget, handled by sliding windows in Phase 2/3.
- **Leakage check**: 17.5% of violating MRT traces mention "secondary task" in visible text (0% of compliant) — agents that slipped up. That's a legitimate catch, but I report metrics both with and without these traces.
